# 2. M3:服务注册与发现

## 2.1 三个角色,别搞混

```
┌─────────────┐   ①注册地址   ┌──────────────┐
│  Provider   │ ───────────▶ │   注册中心     │
│ (服务提供方) │              │  Registry     │
└─────────────┘              └──────────────┘
       ▲                             │
       │ ③真网络调用                  │ ②发现地址
       │                             ▼
┌─────────────┐              ┌──────────────┐
│  Consumer   │ ◀─────────── │  地址列表      │
│ (服务消费方) │              │ ["ip:port",…]│
└─────────────┘              └──────────────┘
```

**关键认知:注册中心里存的是「地址」,不是「实现对象」。**

| | `ServiceProvider` | `ServiceRegistry` |
|---|---|---|
| 存什么 | **实现对象**(`HelloServiceImpl` 实例) | **地址**(`"127.0.0.1:28899"`) |
| 在哪 | **Provider 进程内** | 注册中心(将来是 ZK,跨机器) |
| 干什么 | **执行**("谁来干") | **找到**("去哪找") |

> **为什么必须分成两个类?**
> Provider 在另一台机器上,您没法把它的对象塞进您的内存。
> 您能拿到的只有"去 127.0.0.1:28899 找它" —— 所以跨进程只能传地址。

## 2.2 优雅下线:`start()` 是阻塞的,那怎么停?

**问题:** `NettyServer.start()` 里最后一句是
```java
channel.closeFuture().sync();   // 阻塞在这里不动了
```
它自己**没有任何办法"返回"**。

**解法:从另一个线程调 `close()`。**

```java
// ServerDemo 里
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    registry.unregister(serviceName, address);   // ① 先从注册中心摘掉自己
    server.close();                              // ② 再关服务器
}));
server.start();   // 主线程阻塞在这里
```

**顺序很重要:先注销,再关闭。**
反过来会出现"服务器已经关了,但注册中心里还能查到它"的窗口期 → Consumer 拿到死地址。

**Ctrl+C 时 JVM 会:**
```
1. 收到 SIGINT → 启动已注册的所有 shutdown hook(并发执行)
2. 等 hook 跑完
3. 进程退出
```

## 2.3 本地注册中心的三条局限(面试必答)

| # | 局限 | 后果 |
|---|---|---|
| 1️⃣ | **只活在单个 JVM 内存里** | Provider 和 Consumer 在不同进程时,**Consumer 根本读不到** |
| 2️⃣ | **不持久化** | 注册中心重启,数据全丢 |
| 3️⃣ | **无上下线感知** | Provider 挂了,注册中心不知道,Consumer 还会拿到死地址 |

> **前两条能忍,第三条致命** → 所以 M3 第 4 步要换 ZooKeeper,
> 用**临时节点**让"会话断开 → 节点自动删除",天然解决第 3 条。

**这也是 `M3LocalDemo` 为什么必须写在同一个 JVM 里的原因** ——
它验证的是**接线正确**,不是跨进程能力。

# 3. M4:负载均衡

## 3.1 三种策略的真机对比(各 30 次请求,3 台 Provider)

```
Random           28891:9   28892:10  28893:11     ← 均匀但随机,单次不可预期
RoundRobin       28891:10  28892:10  28893:10     ← 完美均匀,且完全可预期
ConsistentHash   28891:18  28892:8   28893:4      ← 样本小时波动大(正常)
```

> ⚠️ **一致性哈希的 18/8/4 不是 bug!**
> 虚拟节点解决的是「**节点**在环上分布不均」,不是「**key** 分布不均」。
> key 只有 10 个时,统计波动本来就很大 —— 打到 10000 个 key 才会接近均匀。

## 3.2 🔥 一个真实的坑:Set 的迭代顺序**不稳定**

**问题:**
```java
// 朴素写法
return addresses.get(index++ % addresses.size());
```
`addresses` 来自 `LocalServiceRegistry`,底层是 `ConcurrentHashMap` + `Set`。
**Set 的迭代顺序由哈希值决定 —— 既不是插入顺序,增删元素后还可能变。**

后果:
```
上一次 index=0 指向 A
这一次 index=0 可能指向 B
→ "轮询"退化成"近似随机"
→ 而且【没有任何报错】,极难排查
```

**解法:进轮询之前先排序。**
```java
List<String> sorted = new ArrayList<>(addresses);
Collections.sort(sorted);          // 把"不确定的顺序"变成"确定的顺序"
return sorted.get(Math.floorMod(index, size));
```

**实测验证(轮询 6 次的落点):**
```
28891 → 28892 → 28893 → 28891 → 28892 → 28893
   [PASS] 轮询呈固定循环(第 4/5/6 次与第 1/2/3 次完全对应)
```

> 💡 **另一个细节:用 `Math.floorMod` 而不是 `%`。**
> `index` 是 `AtomicInteger`,理论上会溢出成负数;
> **负数 `% size` 会得到负数** → `get()` 抛 `IndexOutOfBoundsException`。
> `floorMod` 保证结果恒为非负。

## 3.3 一致性哈希与虚拟节点

**要解决的问题:** Random / RoundRobin 会把同一个用户的请求打到不同机器。
如果服务端有**本地缓存 / 本地状态**(比如按 userId 缓存的会话),换机器 = 缓存失效。

**基本原理:**
```
1. 把 [0, 2^64) 想象成一个"环"
2. 每个服务地址哈希到环上某个点
3. 请求 key 也哈希到环上,然后【顺时针】找第一个节点
```

**实测粘性:**
```
同一个 key "user-123" 连续调用 10 次,始终落在端口: 28891
   [PASS] 一致性哈希:同一 key 恒定落同一台

10 个不同 userId 的落点: [28892, 28892, 28892, 28892, 28893, 28893, 28893, 28892, 28891, 28893]
   [PASS] 不同 key 会分散到不同节点
```

**虚拟节点(每个物理节点 160 个):**

| | 不用虚拟节点 | 用 160 个虚拟节点 |
|---|---|---|
| 环上分布 | 3 个点,极不均匀 | 480 个点,均匀铺开 |
| 数据倾斜 | 可能一台管半个环 | 每台大约 1/3 |
| 增删节点的影响 | 大面积数据迁移 | **只影响相邻的一小段** |

> 最后一行才是虚拟节点真正的价值:**扩缩容时只迁移少量数据**。

**为什么哈希用 MD5 而不是 `String.hashCode()`?**
`hashCode()` 只有 32 位且分布一般,在环上容易扎堆;
MD5 取前 8 字节得到 **64 位**,分布均匀得多。

# 4. M4:容错

## 4.1 Failfast 与 Failover:**只差一个参数**

```java
new RpcClientProxy(resolver, 0);   // Failfast:一次都不重试
new RpcClientProxy(resolver, 3);   // Failover:最多再换 3 个节点试
```

**Failover 的执行流程:**
```
1. resolveAll(serviceName)          → 拿到全部候选地址(已排序)
2. loadBalancer.select(...)         → 决定"先试哪个",排到队首
3. 依次尝试,每次失败就把该地址的连接从池里丢弃
4. 成功就返回;全部失败才抛异常
```

## 4.2 ⚠️ 最重要的设计决策:**超时不能重试**

这是整个 M4 里最值得讲的一点。

```
· 连接失败(连不上 / 连接被拒)
    → 请求【根本没发出去】→ 换一台重试是安全的 ✅

· 调用超时
    → 请求【可能已经到达服务端并且执行完了】,只是响应没回来
    → 这时候重试,可能造成【重复执行】⚠️
      比如"扣款 100 元""下单""减少库存" —— 重试一次就是扣两次
```

**所以代码里把两种失败分开处理:**

```java
try {
    return clientFor(address).sendRequest(request);

} catch (RpcTimeoutException e) {
    // 超时:直接上抛,【不换节点重试】
    throw e;

} catch (Exception e) {
    // 连接类失败:请求没发出去 → 换一台重试是安全的
    discardClient(address);
    // 继续下一个候选节点
}
```

**为此专门引入了 `RpcTimeoutException`**,继承自 `RpcException`,
和普通异常区分开 —— 否则上层没法判断"这次失败该不该重试"。

> 🎤 **面试标准答法:「什么请求不能盲目重试?」**
> 核心是**幂等性**。幂等的(查询、删除)可以重试;
> 非幂等的(扣款、下单、自增)**必须慎之又慎** ——
> 要么加**唯一请求号**做服务端去重,要么干脆不重试。
> **注意:我们协议头里的 `requestId` 正好可以作为去重的钥匙** ——
> 这是把它加进协议的一个额外好处。

## 4.3 实测数据

```
故意注册一个【没有服务监听】的地址: 127.0.0.1:28999
现在共有 4 个地址(其中 1 个是坏的)

Failfast(重试 0 次) 打 20 次 → 失败 5 次
Failover(重试 3 次) 打 20 次 → 失败 0 次
   [PASS] Failfast 会踩到坏节点(失败 > 0)
   [PASS] Failover 能自动绕开坏节点(失败 = 0)
```

**Failfast 失败 5/20 ≈ 1/4** —— 正好等于"4 个地址里 1 个是坏的"的概率,符合预期。

# 5. 这次踩到的两个真实坑

## 5.1 内部类做服务实现 → 反射报 `IllegalAccessException`

```
RPCException: class RpcRequestHandler cannot access a member of
              class M4LoadBalanceDemo$TaggedHelloService with modifiers "public"
```

**原因:反射调用要求「方法 public」**并且**「所在类对调用方可见」**。

我一开始把实现类写成了 Demo 的静态内部类:
```java
static class TaggedHelloService implements HelloService { ... }   // ❌ 默认包级可见
```
它虽然是 `public` 方法,但**类本身不可见**,
而 `RpcRequestHandler` 在另一个包(`com.handwrite.rpc.core.transport`)→ 调不到。

**修法:提成顶层 `public class TaggedHelloService`。**

> 🎯 **这是一条对 RPC 框架很实际的约束:Provider 端暴露的实现类必须是 public。**
> 因为服务端是用反射调的 —— `method.invoke(service, args)`。

## 5.2 Netty 线程不释放 → JVM 挂住不退出(命令超时 300 秒!)

**现象:** main 抛异常后程序不退出,一直挂着。

**原因:**
```java
Thread t = new Thread(() -> server.start());
t.setDaemon(true);        // ← 只让"外层包装线程"成了守护线程
```
**但 Netty 的 `EventLoopGroup` 内部线程【不是守护线程】**,
它们还活着 → JVM 不退出。

**修法:main 用 try/finally 包住,保证任何路径都会 `close()`。**
```java
try {
    ... 全部逻辑 ...
} finally {
    for (NettyServer s : servers) s.close();   // 释放 EventLoop 线程
}
```

> 🎯 **通用教训:凡是"启动了线程/连接池/IO 资源"的程序,
> 都必须有 finally 或 shutdown hook 来兜底。**
> 依赖 GC 或"进程结束会自动回收"是靠不住的。

# 6. 面试问答(这部分最值钱)

| 问题 | 答题骨架 |
|---|---|
| **注册中心为什么存地址不存对象?** | 存对象只能本进程用;Provider 在别的机器上,跨进程只能传"到哪去找"。所以拆成 `ServiceProvider`(存对象,执行用)+ `ServiceRegistry`(存地址,发现用) |
| **`discover` 为什么返回 List 不返回单个地址?** | 同一服务可能有多个实例。返回列表是**负载均衡的前提** —— 有列表才能"选一个",挂了才能"换一个" |
| **本地注册中心有什么问题?** | 三条:不跨进程共享、不持久化、**无上下线感知**。第三条最致命 → 换 ZK 用**临时节点**解决 |
| **Provider 被强杀,注册中心怎么知道它死了?** | 本地版**不知道**;ZK 版靠**会话 + 临时节点**:会话超时 → 节点自动删除 |
| **三种负载均衡怎么选?** | 无状态服务用 Random/RoundRobin;有本地缓存/会话的用一致性哈希 |
| **为什么一致性哈希需要虚拟节点?** | 不用的话节点在环上分布不均(数据倾斜);用了之后增删节点只影响相邻一小段 → **扩缩容时只迁移少量数据** |
| **什么请求不能盲目重试?** | **非幂等**的(扣款/下单)。而且必须区分"连接失败"(可重试)和"超时"(可能已执行,不可重试) |
| **轮询为什么不能直接用注册中心返回的顺序?** | Set 迭代顺序由哈希决定,不稳定 → index 含义漂移 → 轮询退化成随机,且无报错。**解法:先排序** |
| **`Math.floorMod` 和 `%` 有什么区别?** | 负数时:`-1 % 3 = -1`,`Math.floorMod(-1,3) = 2`。计数器溢出成负数时,`%` 会让 `get()` 越界 |
| **反射调用的可见性要求?** | 方法 public **且**所在类对调用方可见。内部类默认包级可见,跨包反射会失败 → **服务实现类必须 public 顶层类** |
